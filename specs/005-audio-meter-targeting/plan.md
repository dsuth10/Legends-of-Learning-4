# Implementation Plan: Audio Meter Targeting

**Branch**: `main` (spec directory pinned via `.specify/feature.json`) | **Date**: 2026-09-21 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `/specs/005-audio-meter-targeting/spec.md`

## Summary

Extend the existing classroom volume meter so a quiet-time session can be scoped to the whole class, one or more clans, and/or individual students, and make the reward tiering correct and trustworthy. A new `audio_meter_sessions` table records the participant snapshot, the settings locked at start, and the server-side trigger count. Three new endpoints (start, trigger, complete) replace the current pattern where the browser computes the payout and the server trusts it: the server now derives every award as `ceil(base / 2**triggers)` with a floor of 1. HP damage on trigger becomes an opt-in setting that defaults to off, and per-character audit rows make reduced rewards visible to students on the page they already have.

## Technical Context

**Language/Version**: Python 3.8+ backend, ES2017-era vanilla JavaScript on the client (no build step)

**Primary Dependencies**: Flask, Flask-Login, SQLAlchemy, Alembic, Pydantic, Jinja2, Bootstrap 5 (CDN). Browser Web Audio API for microphone RMS. No new dependency is introduced.

**Storage**: SQLAlchemy over SQLite in development (`instance/legends.db`). One new table, `audio_meter_sessions`, via an Alembic migration. Reusable settings stay in the existing `classroom_tool_configs.config_data` JSON column.

**Testing**: pytest with fixtures from `tests/conftest.py`. Service-level unit tests for the tier formula and participant resolution; route-level tests for the three endpoints including authorization and tamper attempts.

**Target Platform**: Flask web app. Teacher-facing projector display in a desktop Chromium/Firefox browser with microphone permission; student-facing surface is the existing Progress page.

**Project Type**: Server-rendered web application with blueprint-organised routes and progressive-enhancement JavaScript.

**Performance Goals**: Microphone analysis stays on the existing `requestAnimationFrame` loop at display refresh rate. Session endpoints are called at most a few times per session (once at start, once per noise trigger, once at completion), so no polling load is added. Completion must award a class of roughly 30 characters in a single transaction well within a normal request.

**Constraints**: No WebSocket or SSE infrastructure exists in this repo and none is added. Award amounts must not be client-supplied. Existing classroom tool settings rows must keep working without a data migration. Cursed Die and behavior-infraction workflows must be untouched.

**Scale/Scope**: One active session per classroom, roughly 20-35 participants per session. Around three backend files touched plus one new model, one new service, one migration, two templates, and two JavaScript files.

## Implementation phases

### Phase A - Data and service foundation

1. `app/models/audio_meter.py`: `AudioMeterSession` per [data-model.md](data-model.md), plus a `str`-backed `AudioMeterSessionStatus` enum following the `FallenStatus` pattern in `app/models/behavior.py`.
2. Register the model in `app/models/__init__.py` `init_db()` and in `migrations/env.py`.
3. Alembic revision creating `audio_meter_sessions`; run `alembic upgrade head`.
4. `app/services/audio_meter.py`:
   - `tier_amount(base, triggers)` - integer ceiling halving with a floor of 1.
   - `resolve_participants(classroom, target_type, clan_ids, student_ids)` - returns a deduplicated list of active characters, validating that every clan and student belongs to that classroom.
   - `start_session(...)`, `record_trigger(...)`, `complete_session(...)`, `abandon_active_sessions(classroom_id)`.
   - Per-character and batch `AuditLog` writes with the `description` key the student feed reads.

### Phase B - Endpoints

5. Add `hp_damage_enabled: False` to `DEFAULT_VOLUME_CONFIG` and coerce it in the settings POST.
6. Add four endpoints to `app/routes/teacher/classroom_tools.py`, each with Pydantic validation and an ownership check: participant targets (read), session start, session trigger, session complete. Contract in [contracts/audio-meter-api.md](contracts/audio-meter-api.md).
7. Leave `api_volume_penalty` and `api_volume_reward` in place for now; the display stops calling them once Phase C lands, and their removal is a follow-up so a stale open display cannot break mid-lesson.

### Phase C - Client and templates

8. `classroom_tools_display.html` / `classroom_tools_display.js`: pass the new session URLs and the classroom roster entry point into the tool config.
9. `volume_meter.js`: add the participant picker (whole class, clan checkboxes, student checkboxes) shown before start; call start to obtain a session id; call trigger on each sustained breach and render the authoritative payout it returns; call complete when the countdown reaches zero, sending accumulated pause time; keep the existing RMS detection untouched.
10. `classroom_tools.html` / `classroom_tools_config.js`: add the HP damage toggle, defaulting to off, and keep the damage amount field meaningful only while the toggle is on.

### Phase D - Tests

11. `tests/test_audio_meter.py`: tier formula table covering 0-3 triggers on 1000 XP / 100 gold and the floor-of-1 case; participant dedup across clan plus individual selection; non-participants unchanged; HP off by default and applied only when enabled; completion before the timer elapses rejected; an inflated request body granting no more than the derived amount; ownership 403s; per-character audit rows present with a description.

## Key design decisions carried from research

- Session state lives in a dedicated table because a client-held trigger count cannot satisfy the trust requirement (research D1, D3).
- Participants are snapshotted at start, so a mid-session clan change cannot alter who gets paid (D2).
- `tier_amount` uses `-(-base // 2**n)` for exact integer ceiling division, which is why 100 gold becomes 13 rather than 12 at the third tier (D4).
- HP damage bypasses `app/services/behavior.py` deliberately: routing through it would create `BehaviorIncident` rows and possibly `FallenEvent` rescue windows, which the spec excludes (D5).
- Per-character `TOOL_REWARD` audit rows with a `description` surface on the existing student Progress activity feed, so student visibility needs no student-side code (D7).
